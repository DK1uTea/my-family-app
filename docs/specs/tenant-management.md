# Spec: Tenant Management

## Objective

Give `super_admin` a page to search and manage tenants. The backend remains authoritative
for access and derives tenant scope from the verified user session; the page does not send
tenant headers.

## Assumptions

- Route and module key: `tenant-management`.
- Only `super_admin` receives the permission/navbar entry and can open the page.
- List search matches tenant name and ID. Search, page, limit, and sort are URL-backed;
  page size defaults to 10 and the backend caps it at 100. Sort accepts `createdAt:desc`
  (Newest, default) or `createdAt:asc` (Oldest).
- Tenant status is represented by `isActive`. Deactivation preserves tenant data and blocks
  its users at the next API request.
- Tenant IDs are generated by the backend from a short normalized name slug and UUID
  suffix, remain within 50 lowercase letters, digits, or hyphens, and are immutable.
  Tenant names are 1–150 characters. Descriptions are optional and at most 500 characters.
  Editing changes the name and description only.

## Scope and behavior

- The sidebar shows Tenant Management only when `/api/users/me` grants its navbar key.
- The page is guarded by the tenant management permission. Unauthorized API requests return
  403 even if a caller bypasses the page guard.
- A responsive SearchFilterBar exposes a flexible-width search field and Newest/Oldest
  sort filter. Changing search or sort resets the page to 1 and updates URL state.
- A paginated table shows tenant ID, name, description, status, created date, and a row OptionMenu.
- Add Tenant opens an accessible Sheet with labeled name and optional description fields.
  Each field has a localized placeholder, and the backend generates the tenant ID.
  Successful create closes the Sheet and refreshes the list.
- Edit opens a Sheet prefilled with the tenant name and description. Successful save refreshes the list.

## Data and architecture

- `GET /api/tenants?search=&page=&limit=&sort=createdAt:desc` returns
  `{ items, pagination }` inside the standard response envelope. `pagination` conforms to shared `PaginationType`:
  `{ total, limit, page, totalPages, hasNextPage, hasPrevPage }`.
- `POST /api/tenants` accepts `{ name, description? }`; the backend generates the immutable tenant ID and returns it in the created tenant.
- `PATCH /api/tenants/{id}` accepts `{ name, description? }`.
- `PATCH /api/tenants/{id}/activate` activates a tenant; it has no request payload.
- `PATCH /api/tenants/{id}/deactivate` deactivates a tenant; it has no request payload.
- Use TanStack Query for data and mutations. Keep the list query in `useTenants`; expose
  create, rename, and status mutations as separate hooks. Invalidate the tenant list after
  each successful mutation.
- Use nuqs for search, page, limit, and sort URL state. Do not store these in local state.
- Implement as a sidebar module using the shared SearchFilterBar, Table, OptionMenu,
  Pagination, and Sheet components.
- Add feature strings and navigation labels to both locale files.

## QA coverage (QA-owned)

- Super admin sees the sidebar route and can search, paginate, create, edit, activate, and
  deactivate tenants.
- Tenant roles do not see the route and receive 403 from tenant endpoints.
- Search resets pagination; URL state restores search and page; mutations update the list.
- Form validation is announced accessibly; the Sheet works by keyboard and create returns the generated ID.
- Loading, empty, API error, and both locales render correctly.

## Success criteria

- The specified operations work through real backend APIs for an authenticated super admin.
- Search and pagination are URL-backed and match server results.
- The page is hidden/guarded for tenant roles and APIs independently enforce authorization.
- Both locales are complete and accessibility checks pass.

## Seed defaults

- Migration and seed use tenant ID `default`, name `Default Tenant`.
- Tenant ID is backend-generated and immutable after creation; tenant name is editable.
- Super admin is the configured `SEED_SUPER_ADMIN_EMAIL` account; the three tenant role
  account credentials are supplied through the env variables in the backend spec.
